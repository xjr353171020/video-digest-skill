# Video Digest Skill：可靠的视频证据提取与高密度摘要

状态：已完成产品与架构决策，等待实现。

## Problem Statement

用户经常遇到时长很长、信息密度未知的 YouTube 或哔哩哔哩视频。完整观看会消耗大量时间，倍速播放仍要求持续注意，而把整段视频机械转成文稿也不是最终目的。用户真正需要的是快速判断视频是否值得看、提取独有且与决策相关的信息、定位少数值得观看的片段，并在必要时核查关键事实。

当前原型已经具备字幕优先、无字幕转写、按需抽帧、“是否值得看”、事实与观点分离以及频道摘要等正确的产品方向，但证据获取层还不够可靠。现有流程可能一次请求过多字幕轨道、吞掉外部命令的真实错误、在轻量字幕路径失败后过早下载音频、把旧转录文件误认为本次成功、在所谓自动视觉模式下直接下载视频，以及在详细处理成功前过早把频道视频标记为已处理。登录态、限流、依赖缺失和站点变化也没有形成一致且可诊断的失败模型。

因此，需要把“获取可信、可追溯的视频证据”和“基于证据生成高密度摘要”明确分层，使 Skill 在 Windows 上能够可靠处理 YouTube 与哔哩哔哩的常见路径，同时保护浏览器登录态和本地凭证，并且不会为了摘要而默认下载完整视频。

## Solution

构建一个面向 Codex 的 Video Digest Skill。用户提供单个视频、多个视频或频道请求后，Skill 先识别平台和任务意图，再通过平台证据适配器按成本从低到高获取元数据、字幕、必要时的本地语音转写，以及仅在确有必要时获取的视觉证据。

所有证据路径都汇总为统一的“证据包”。证据包只保留摘要真正需要的精简元数据、带来源和时间范围的转录片段、可选视觉观察、每次获取尝试的结果、警告以及数据是否外发等来源信息。摘要层只消费证据包，不直接依赖某个站点、浏览器或命令行工具的原始输出。

YouTube 优先使用可用的官方 Chrome transcript 或轻量字幕接口，并且只选择一个最合适的字幕轨道；哔哩哔哩优先使用当前浏览器登录会话或本地 B 站字幕工具。只有确实没有可用字幕时，才下载音频并用本地 faster-whisper CPU INT8 转写。视觉分析采用两阶段决策：先根据请求和文本证据判断画面是否必要，再只读取相关时间窗口的少量帧或浏览器截图。

最终输出先回答“值不值得看”，再给出核心信息、真正新增的信息、关键时间点、事实与观点区分、值得观看和可以跳过的片段、证据不足之处，以及预计节省的时间。多视频和频道模式会进一步比较重复度、独有信息和单位时间价值。

## User Stories

1. 作为想节省时间的用户，我想粘贴一个 YouTube 视频链接并快速获得高密度摘要，从而不必先完整观看视频。
2. 作为想节省时间的用户，我想粘贴一个哔哩哔哩视频链接并获得相同风格的摘要，从而不必为不同平台学习不同工作流。
3. 作为只关心结论的用户，我想先看到视频是否值得完整观看，从而可以在几十秒内决定下一步。
4. 作为时间有限的用户，我想看到建议观看的具体时间段，从而只消费最有价值的片段。
5. 作为时间有限的用户，我想看到可以跳过的开场、重复、广告和铺垫，从而避免低价值内容。
6. 作为注重效率的用户，我想看到信息密度和完整观看价值评分，从而能比较摘要价值与观看成本。
7. 作为注重效率的用户，我想看到预计节省的观看时间，从而直观理解本次摘要的收益。
8. 作为有明确问题的用户，我想指定只分析某个主题或问题，从而避免接收与当前目标无关的内容。
9. 作为有明确问题的用户，我想让摘要优先回答我的问题，再补充视频的其他关键结论，从而让输出更贴近决策。
10. 作为需要追溯证据的用户，我想让重要结论带有真实可用的时间戳，从而能快速回到原视频核对。
11. 作为需要追溯证据的用户，我想知道每条重要信息来自人工字幕、自动字幕、本地转写还是画面观察，从而判断证据质量。
12. 作为需要追溯证据的用户，我想让系统在没有时间戳时明确省略时间戳，从而避免虚构定位信息。
13. 作为面对长视频的用户，我想让系统分段处理完整转录并去重，从而不会因为上下文过长而漏读后半段。
14. 作为面对长视频的用户，我想让系统在给出精确或争议性结论前重新核对相关转录区间，从而降低摘要失真。
15. 作为面对重复表达的用户，我想看到压缩后的独有观点而不是逐段复述，从而真正减少阅读时间。
16. 作为观看访谈或评论视频的用户，我想区分事实、观点、预测、轶事和推广内容，从而不会把说话者立场误当成事实。
17. 作为担心视频夸大的用户，我想在要求时核查少量决定性事实，从而知道视频核心结论是否可信。
18. 作为担心视频夸大的用户，我想看到每条核查结论的支持程度与关键限制，从而不会把复杂证据压缩成简单真假标签。
19. 作为不需要事实核查的用户，我想默认只做视频摘要，从而避免无谓增加等待时间和联网请求。
20. 作为观看新闻或时效性内容的用户，我想让系统识别需要当前信息验证的关键说法，从而不会依据过时事实做判断。
21. 作为观看软件教程的用户，我想让系统在操作步骤只出现在屏幕上时读取必要画面，从而不会因为字幕缺失视觉步骤而得到残缺摘要。
22. 作为观看图表或演示视频的用户，我想让系统只分析与核心结论相关的画面区间，从而避免下载和处理整段视频。
23. 作为观看普通口播视频的用户，我想让系统默认不下载视频或抽帧，从而用最低成本获得摘要。
24. 作为明确要求视觉分析的用户，我想强制启用视觉证据，从而能检查图表、代码、界面或产品展示。
25. 作为不希望视觉分析的用户，我想明确关闭视觉证据，从而控制下载量和处理时间。
26. 作为使用中文字幕的用户，我想优先选择符合请求语言的人工字幕，从而获得最准确且最自然的证据。
27. 作为使用自动字幕的用户，我想在没有人工字幕时自动选择一个最合适的自动字幕轨道，从而避免不必要的语音转写。
28. 作为处理多语言视频的用户，我想让系统只请求一个明确选定的字幕轨道，从而避免批量下载自动翻译字幕和触发限流。
29. 作为处理外语视频的用户，我想让摘要使用我的语言表达，同时保留原始证据语言和来源，从而兼顾可读性与可追溯性。
30. 作为处理无字幕视频的用户，我想让系统只下载音频并在本机转写，从而避免下载完整视频和把音频默认发送给第三方。
31. 作为使用 CPU 的 Windows 用户，我想让本地转写采用适合 CPU 的默认配置，从而在准确率、耗时和资源占用之间取得合理平衡。
32. 作为首次使用本地转写的用户，我想在模型尚未安装或需要下载时先得到明确提示，从而知道预计成本并能决定是否继续。
33. 作为不允许云端转写的用户，我想让系统在本地转写不可用时停止并说明原因，从而不会静默把音频外发。
34. 作为愿意使用可选云服务的用户，我想让任何云端转写成为单独、明确的选择，从而能够知情决定数据外发。
35. 作为已登录视频平台的用户，我想让 Skill 使用当前本地浏览器会话读取我本来就能访问的字幕，从而不必手动导出 Cookie。
36. 作为已授权使用浏览器登录态的用户，我想让凭证只在本机、仅为目标站点请求使用，从而降低账户泄露风险。
37. 作为重视隐私的用户，我想确保 Cookie、令牌和 API Key 不会出现在提示词、摘要、日志、截图或生成的证据文件中，从而保护账户安全。
38. 作为重视隐私的用户，我想让系统在浏览器数据库被占用时使用其他受支持的登录态路径或给出明确说明，从而不会强行复制或破坏浏览器数据。
39. 作为重视安全的用户，我想让系统拒绝绕过 DRM、付费墙或我无权访问的控制，从而保持合法合规。
40. 作为遇到失败的用户，我想知道失败发生在元数据、字幕、认证、限流、音频、转写还是视觉阶段，从而能采取正确措施。
41. 作为遇到失败的用户，我想看到经过脱敏的原始错误类别、退出状态和建议操作，从而不会只收到笼统的“不可用”。
42. 作为遇到平台限流的用户，我想让系统避免无界重试并提供可重试状态，从而减少进一步封禁风险。
43. 作为重复运行同一视频的用户，我想确保本次失败不会误用以前成功运行留下的转录，从而不会得到看似成功但已过期的摘要。
44. 作为重复运行同一视频的用户，我想在证据未变化且缓存仍有效时复用安全的缓存，从而减少重复请求和处理时间。
45. 作为需要诊断的用户，我想看到本次运行唯一对应的获取报告和证据来源，从而可以复现问题而不会混淆旧文件。
46. 作为不想占用磁盘的用户，我想让临时音频、视频和帧在成功处理后按策略清理，从而只保留必要的转录、证据摘要和报告。
47. 作为需要调试的用户，我想选择保留本次生成的临时媒体，从而能够复查转写或视觉问题。
48. 作为比较多个视频的用户，我想获得统一格式的并排比较，从而快速判断哪一个最值得看。
49. 作为比较多个视频的用户，我想看到视频之间重复、矛盾和各自独有的信息，从而避免重复消费相同观点。
50. 作为比较多个视频的用户，我想知道哪一个视频的单位时间信息价值最高，从而只选择最佳来源。
51. 作为批量处理视频的用户，我想让单个视频失败不影响其他视频完成，从而仍然得到可用的部分结果。
52. 作为关注多个频道的用户，我想扫描指定时间范围内的新视频，从而得到每日或每周视频情报。
53. 作为关注多个频道的用户，我想按主题、频道优先级和潜在信息价值先做轻量筛选，从而只深入处理值得看的候选。
54. 作为关注多个频道的用户，我想让频道优先级只影响检查顺序而不影响可信度评分，从而避免把偏好误当成证据质量。
55. 作为关注多个频道的用户，我想把同一事件的重复报道合并，从而只看到真正新增的信息。
56. 作为关注多个频道的用户，我想让视频只有在摘要成功或我明确忽略后才成为已处理，从而使暂时失败的视频能够自动重试。
57. 作为关注多个频道的用户，我想看到每个视频处于已发现、已排队、处理中、成功、失败、可重试或已忽略状态，从而理解批处理进度。
58. 作为关注多个频道的用户，我想重新处理指定旧视频而不重置全部状态，从而能修复单个失败或更新摘要。
59. 作为 Skill 使用者，我想直接用自然语言请求“值得看吗”“只提取某部分”或“比较这些视频”，从而无需记忆复杂命令。
60. 作为 Skill 使用者，我想在依赖缺失时得到平台相关且可执行的安装提示，从而能自行恢复能力。
61. 作为 Skill 使用者，我想让默认输出使用我的语言并保持紧凑，从而无需再二次整理。
62. 作为 Skill 使用者，我想在证据不足时看到明确的不确定性或无法判断结论，从而不会被虚构的完整摘要误导。
63. 作为维护者，我想让平台差异封装在证据适配器内，从而站点变化不会迫使摘要逻辑整体重写。
64. 作为维护者，我想让所有适配器返回同一种证据包，从而能够用同一摘要流程处理 YouTube、哔哩哔哩和未来平台。
65. 作为维护者，我想让字幕选择、错误分类、缓存和状态提交具有确定性，从而可以稳定回归已发现的问题。
66. 作为维护者，我想让外部工具输出在进入报告前统一脱敏，从而测试和诊断不会泄露凭证或签名 URL。
67. 作为维护者，我想用受控适配器响应端到端测试用户请求到摘要结果，从而只验证外部行为而不绑定命令实现。
68. 作为维护者，我想用少量真实公开视频做显式的在线健康检查，从而及时发现站点或工具变化而不让普通测试依赖网络。
69. 作为维护者，我想让在线健康检查与离线验收测试分开，从而网络波动不会使核心测试不稳定。
70. 作为维护者，我想保留原型中已经有效的摘要模板和频道配置语义，从而升级证据层时不会无谓破坏用户体验。

## Implementation Decisions

- 产品继续以 Codex Skill 为入口。Skill 负责识别用户意图、选择证据路径、调用本地或已连接工具、读取统一证据包，并按固定摘要契约生成结果。
- 核心领域对象包括：视频请求、获取尝试、精简元数据、转录片段、视觉观察、证据包、摘要结果和频道处理状态。平台原始响应不得直接成为摘要层接口。
- 建立证据获取编排器和可替换的证据适配器。编排器根据平台、当前环境、认证可用性、用户要求和前一次失败类别选择下一条路径。
- 证据包至少记录规范化视频身份、平台、标题、作者或频道、时长、发布日期、语言、章节、带起止时间的转录片段、转录来源、可选视觉观察、获取尝试、警告、完整度和数据处理边界。
- 摘要层默认只读取精简元数据，不读取包含大量媒体格式、签名地址或无关字段的完整站点元数据。完整原始元数据只可作为本地诊断产物保留，不能默认进入模型上下文。
- YouTube 在已连接 Chrome 且 transcript 可用时优先使用官方浏览器 transcript；否则优先使用轻量字幕路径，再使用定向的 yt-dlp 字幕路径。只有所有字幕路径都没有得到可用证据时才进入本地 ASR。
- YouTube 字幕选择必须先枚举可用轨道，再按用户请求语言、人工字幕优先、原始语言优先、自动字幕次之的规则选择一个轨道。只有用户明确需要翻译时才能选择一个目标翻译轨道，禁止使用会扩展成大量翻译字幕的宽泛语言表达式。
- 哔哩哔哩优先使用当前浏览器页面会话或本地 B 站字幕工具获取原生字幕。若字幕接口需要登录，应使用本地隐藏凭证配置或当前浏览器会话；不得要求用户把 Cookie 粘贴到对话。
- 浏览器 Cookie 数据库的直接复制、解密或强制解锁不是主流程要求。浏览器数据库被占用时，系统应改用已连接浏览器会话、受支持的本地 Cookie 读取能力或返回需要用户操作的明确状态，不能冒险破坏浏览器数据。
- 第三方视频解析网站和第三方 B 站直链服务不作为默认依赖。未来若增加，必须是明确启用的独立适配器，并在运行前说明 URL、字幕或媒体会发送给哪个服务。
- 无字幕回退只下载满足转写所需的音频。默认本地转写引擎为 faster-whisper，Windows CPU 默认使用 INT8；模型大小可配置，但首次模型下载必须显式报告。
- 本地转写生成的片段需要保留开始时间、结束时间、文本、语言和转写来源。引擎没有可靠置信度时不得伪造精确置信度。
- 云端 ASR 不属于默认路径。若以后支持，必须采用独立开关、明确的数据外发提示以及本地安全凭证存储。
- 视觉模式分为关闭、自动和强制。关闭永不获取画面；强制按用户要求获取必要画面；自动必须先分析请求、转录完整度和屏幕引用，再形成带原因与目标时间窗口的视觉需求决定。
- 自动视觉模式不得等同于无条件开启。视觉证据优先通过当前浏览器的目标时间截图获得；无法使用浏览器时，才获取满足目标区间分析所需的最低质量视频流和少量帧。
- 视觉观察必须包含时间点或时间范围、观察内容和触发原因。摘要中的画面结论必须与语音或字幕结论分开标记。
- 每次运行拥有唯一运行身份和独立产物清单。任何成功判断都必须引用本次运行清单中登记的文件或适配器结果，不能仅因固定目录中存在旧转录文件而成功。
- 缓存按视频身份、字幕轨道、内容版本、适配器版本和相关请求参数校验。缓存命中必须在证据包中可见；无效或不完整缓存不得参与本次摘要。
- 获取报告采用统一状态和错误分类，包括成功、部分成功、不可用、需要认证、需要用户同意、缺少依赖、被限流、站点阻止、超时、解析失败和不受支持。
- 外部命令的退出状态、标准错误摘要和阶段信息必须保留并脱敏。错误报告不得包含 Cookie、授权头、API Key、签名媒体地址或浏览器数据库内容。
- 限流和暂时性错误采用有界重试与退避。重试次数耗尽后保留可重试状态，不把它伪装成永久无字幕。
- 摘要结果使用稳定契约：视频身份、一句话结论、核心信息、真正新增的信息、关键论据、事实与观点区分、证据不足、建议观看片段、可跳过片段、信息密度、完整观看价值、最终建议和预计节省时间。
- 信息密度评价基于单位时长内独有且与决策相关的信息，不把语速、剪辑速度、播放量或频道优先级当作信息密度。
- 值得观看建议分为完整观看、只看指定片段、看摘要即可和跳过。建议必须能由证据完整度、独有信息、行动价值和视觉必要性解释。
- 证据包没有可靠时间戳时，摘要不得生成看似精确的时间范围。证据不足以支持结论时，结果必须降级为部分摘要或无法判断。
- 长转录按章节或自然时间段分块。每块先提取主张、证据和时间戳，再合并、去重；精确结论在输出前重新定位到原始片段。
- 事实核查是摘要后的可选阶段。只核查影响核心结论或用户决策的少量事实，优先原始研究、官方文件和第一方资料，并把外部核查与视频自身证据分开呈现。
- 多视频请求为每个视频生成独立证据包和摘要，再生成跨视频比较。单个视频失败不得中止其他视频，失败项应在总结果中保留原因。
- 频道发现与详细处理分离。发现新视频只创建待处理记录，不能立即提交为已处理。
- 频道状态以视频身份记录已发现、已排队、处理中、成功、失败、可重试和已忽略。只有成功生成满足最低证据要求的摘要，或用户明确忽略，才能从后续默认队列中排除。
- 频道摘要在视频级处理之后按主题聚类、识别重复论点、保留独有信息，并给出单位时间价值排序。高优先级频道只提前检查，不自动获得更高可信度或推荐分。
- 默认保留转录、精简证据包、获取报告和最终摘要。下载的音频、视频和临时帧在成功后按受控策略清理；调试或用户明确要求时可以保留。清理只能作用于本次运行明确登记的生成产物。
- 安装与诊断应适配 Windows PowerShell。依赖检查分别说明核心依赖、平台适配器依赖、本地 ASR 依赖和可选视觉依赖，避免把所有依赖强制安装在最小字幕路径中。
- 迁移时保留原型中已经确定的自然语言触发方式、摘要结构、评分维度、事实核查分类和频道配置语义；替换不可靠的证据获取、状态提交和临时产物管理实现。

## Testing Decisions

- 主测试只使用一个最高层接缝：“用户视频请求 → 受控证据适配器 → 规范化证据包 → 最终摘要与观看建议”。这是功能验收的主要入口。
- 好测试只断言用户可观察行为和稳定领域契约，例如选择了哪类证据、是否正确回退、是否保留来源与时间戳、是否暴露不确定性、最终建议是否符合受控证据，以及频道状态是否正确提交。测试不应断言具体子进程参数排列、内部函数调用次数或第三方响应的完整原始形状。
- 主测试通过注入可控适配器和可控摘要生成器运行完整工作流。摘要文本不要求逐字匹配，但结构化结论、来源引用、推荐类别和禁止行为必须可断言。
- 当前项目没有既有自动化测试或可复用测试惯例，因此以受控场景测试作为新的基线；此前的真实运行结果只作为场景设计证据，不作为持续通过的自动化测试。
- 必须覆盖 YouTube 人工字幕一次成功，并验证不会下载音频或视频。
- 必须覆盖 YouTube 轻量字幕成功，并验证精简元数据和时间戳进入证据包。
- 必须覆盖 yt-dlp 字幕触发限流后转向另一条轻量路径，并验证真实失败类别没有被吞掉。
- 必须覆盖存在大量自动翻译轨道的场景，并验证只选择一个字幕轨道。
- 必须覆盖同一视频前一次成功、后一次失败的场景，并验证旧转录不会使本次运行误报成功。
- 必须覆盖哔哩哔哩通过已连接浏览器或本地字幕工具取得中文字幕的场景。
- 必须覆盖哔哩哔哩需要认证但没有可用登录态的场景，并验证结果为需要认证而不是无字幕。
- 必须覆盖浏览器 Cookie 数据库被占用的场景，并验证工作流不会强制复制或泄露数据库内容。
- 必须覆盖没有字幕但音频可取得的场景，并验证只下载音频、调用本地 ASR、保留转录来源且不下载完整视频。
- 必须覆盖本地 ASR 依赖或模型缺失的场景，并验证系统在下载或处理前返回明确、可操作的状态。
- 必须覆盖普通口播视频的自动视觉判断，并验证不获取画面。
- 必须覆盖字幕无法表达图表或界面内容的场景，并验证自动视觉只请求相关时间窗口。
- 必须覆盖用户强制开启和关闭视觉模式的场景，并验证用户选择优先于自动判断。
- 必须覆盖时间戳缺失、时间戳不连续和转录部分成功的场景，并验证不会生成虚假定位。
- 必须覆盖超长转录的分块、合并、去重和精确主张回查。
- 必须覆盖事实、观点、预测、轶事和推广内容的区分，以及证据不足时的降级表达。
- 必须覆盖多视频请求中的部分失败、重复论点识别、独有信息比较和最佳单位时间价值推荐。
- 必须覆盖频道发现不提交已处理、成功后提交、失败后保留可重试、用户明确忽略后排除，以及指定旧视频重新处理。
- 必须覆盖报告和所有持久产物的敏感信息扫描，确保 Cookie、授权头、API Key、签名 URL 和浏览器数据库内容不会出现。
- 必须覆盖临时媒体清理只作用于本次运行登记产物，并验证调试保留选项不会删除这些产物。
- 第三方站点、Chrome、B 站工具和本地 ASR 的真实调用采用独立的显式在线健康检查，不参与普通离线测试。健康检查使用公开或用户有权访问的视频，限制频率，并记录日期、来源、轨道、认证边界和是否发生数据外发。
- 首次交付至少完成五类真实验收：有字幕 YouTube、中文字幕 YouTube、带登录态字幕的哔哩哔哩、无字幕本地 ASR、确实需要视觉证据的视频。任何在线验收失败都应归类为产品缺陷、外部服务变化或环境限制，不能以 Skill 已加载代替行为验证。

## Out of Scope

- 绕过 DRM、付费墙、会员权限、地区限制或其他访问控制。
- 要求用户在聊天中粘贴 Cookie、会话令牌、API Key 或账号密码。
- 默认复制、解密或长期保存 Chrome Cookie 数据库。
- 默认把音频、字幕或视频发送给第三方解析、转写或总结服务。
- 对直播流进行实时摘要、监控或边播边总结。
- 逐帧理解整段长视频、完整视觉索引或视频搜索引擎。
- 视频下载管理、视频剪辑、自动生成短视频或重新发布内容。
- 自动导出完整翻译字幕、配音、说话人分离或专业级逐字稿校对。
- 在第一版中承诺支持所有 yt-dlp 可识别站点；第一版只对 YouTube 和哔哩哔哩承担明确验收责任。
- 把播放量、点赞数、频道优先级或模型主观喜好当作视频可信度结论。
- 对视频中的每一句话进行全面事实核查，或承诺对所有争议性主题给出确定真相。
- 自动创建定时任务或后台常驻服务；频道摘要提供可调用的批处理能力，调度由独立工作流处理。
- 建设通用操作系统凭证管理器；本功能只使用现有浏览器会话、已有本地安全配置和最小必要授权。
- 把本地音视频文件导入作为第一版主要入口；第一版聚焦网页视频 URL 和频道。
- 在本规格内完成项目 Git 仓库、远端仓库或 issue tracker 的创建与配置。

## Further Notes

- 领域词汇：证据适配器负责从单一来源获取信息；获取尝试记录一次适配器调用及其结果；证据包是摘要层唯一允许消费的平台无关输入；视觉需求决定记录为什么以及在哪些时间窗口需要画面；摘要结果是面向用户的最终输出；频道处理状态决定视频是否需要再次进入队列。
- 第一条可独立验证的垂直切片应为：单个有字幕 YouTube 请求，经轻量字幕适配器形成证据包，输出带真实时间戳的高密度摘要和观看建议，并证明没有下载音频或视频。
- 第二阶段增加哔哩哔哩登录态字幕与统一错误分类；第三阶段增加本地 faster-whisper 回退；第四阶段增加真正按需的视觉决策；第五阶段增加多视频和频道状态机；事实核查可在稳定摘要契约之上增量接入。
- 原型可以继续作为产品行为参考，但在字幕选择、错误保留、运行隔离、自动视觉和频道状态提交得到修复前，不应直接作为最终 Skill 安装。
- 项目当前没有领域词汇表、ADR 或自动化测试约定。本规格因此记录了本次对话中冻结的词汇和决策；发布到 tracker 时应以本文为 issue 正文，并只添加 `ready-for-agent` 标签。
